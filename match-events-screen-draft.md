# Черновик документации: экран событий матча за вчерашний день

## Контекст задачи

Нужно подготовить мобильный экран, на котором пользователь видит события,
произошедшие в матчах чемпионата за вчерашний день.

Исходная модель данных на схеме содержит сущности:

- `Country`
- `Champ`
- `Match`
- `Team`
- `Event`
- `EventGroup`

### Итог задания 1. Пользовательский сценарий

1. Пользователь открывает экран просмотра событий.
2. Приложение отображает список матчей, сгруппированный или отфильтрованный по
   выбранной дате.
3. По умолчанию приложение показывает матчи за вчерашний день.
4. Пользователь может изменить дату отбора матчей через фильтр даты.
5. Пользователь может дополнительно отфильтровать список матчей по чемпионату.
6. В списке матчей приложение отображает основные данные по каждому матчу:
   - название чемпионата;
   - команды-участники;
   - время начала матча;
   - финальный счет, если матч завершен;
   - статус матча.
7. Список матчей сортируется по времени начала матча от более раннего к более
   позднему.
8. Пользователь выбирает матч из списка.
9. Приложение открывает экран или блок событий выбранного матча.
10. Приложение отображает список событий матча в порядке их появления по ходу
    матча.
11. Если у выбранного матча нет событий, приложение отображает пустой список с
    текстом: "События отсутствуют".

## Задание 2. Методы API для поддержки функциональности

Ниже вариант REST API, переписанный уже по ответам из задания 1. Экрану нужны
дата, чемпионат, список завершенных матчей и события выбранного матча.

### 1. Получить список матчей при открытии экрана и изменении фильтров

```http
GET /api/v1/matches
```

Метод вызывается:

1. при открытии экрана с предвыбранными параметрами;
2. повторно, когда пользователь изменил дату;
3. повторно, когда пользователь изменил чемпионат.

На открытии экрана клиент вызывает:

```http
GET /api/v1/matches?date=2026-05-18
```

Если пользователь выбрал чемпионат:

```http
GET /api/v1/matches?date=2026-05-18&championshipId=123
```

#### Query-параметры

| Параметр | Тип | Обязательный | Описание |
| --- | --- | --- | --- |
| `date` | `string` в формате `YYYY-MM-DD` | да | Дата отбора матчей. На первом открытии клиент передает вчерашнюю дату. |
| `timezone` | `string` | нет | Таймзона для границ даты. Если договорились жить по серверному времени, параметр можно не передавать. |
| `championshipId` | `number` | нет | Фильтр по чемпионату. |

#### Правила выборки

- матчи выбираются по `Match.DateStart`;
- показываем только завершенные матчи: `IsFinished = true`;
- если матч начался вчера, а закончился сегодня, он все равно относится ко вчерашней
  дате;
- список матчей сортируется по времени начала от раннего к позднему;
- параметр `status` с клиента не нужен: по текущему решению всегда возвращаем
  завершенные матчи;
- фильтра по группам событий нет: клиент сказал, что он не нужен.

#### Ответ

```json
{
  "items": [
    {
      "id": 987,
      "championship": {
        "id": 123,
        "name": "English Premier League"
      },
      "startAt": "2026-05-18T18:00:00Z",
      "status": "finished",
      "score": {
        "home": 2,
        "away": 1,
        "display": "2:1"
      },
      "teams": {
        "home": {
          "id": 1,
          "name": "Arsenal"
        },
        "away": {
          "id": 2,
          "name": "Chelsea"
        }
      },
      "eventsCount": 6
    }
  ]
}
```

#### Комментарии

- это основной метод для открытия экрана и последующего изменения фильтров;
- сортировка серверная: `DateStart ASC`;
- если матчей нет, возвращаем `items: []`, а клиент показывает пустое состояние.

### 2. Получить список чемпионатов для фильтра

```http
GET /api/v1/championships
```

Метод нужен, если фильтр чемпионата перезагружается отдельно от списка матчей.

#### Query-параметры

| Параметр | Тип | Обязательный | Описание |
| --- | --- | --- | --- |
| `date` | `string` в формате `YYYY-MM-DD` | да | Дата, для которой строим фильтр. |
| `timezone` | `string` | нет | Таймзона для границ даты. |

#### Ответ

```json
{
  "items": [
    {
      "id": 123,
      "name": "English Premier League",
      "matchesCount": 2
    }
  ]
}
```

#### Комментарии

- возвращаем только чемпионаты, где есть завершенные матчи за выбранную дату;
- на клиенте дополнительно добавляем вариант "Все чемпионаты".

### 3. Получить события выбранного матча

```http
GET /api/v1/matches/{matchId}/events
```

#### Path-параметры

| Параметр | Тип | Описание |
| --- | --- | --- |
| `matchId` | `number` | Идентификатор выбранного матча. |

#### Query-параметры

Не нужны. Особенно не нужен фильтр по группам событий: клиент ответил отрицательно,
так что не плодим лишнюю ручку/параметр без пользы.

#### Ответ

```json
{
  "match": {
    "id": 987,
    "championship": {
      "id": 123,
      "name": "English Premier League"
    },
    "startAt": "2026-05-18T18:00:00Z",
    "status": "finished",
    "score": {
      "home": 2,
      "away": 1,
      "display": "2:1"
    },
    "teams": {
      "home": {
        "id": 1,
        "name": "Arsenal"
      },
      "away": {
        "id": 2,
        "name": "Chelsea"
      }
    }
  },
  "items": [
    {
      "id": 555,
      "title": "Гол",
      "value": "Bukayo Saka",
      "matchMinute": 12,
      "sortOrder": 1,
      "occurredAt": "2026-05-18T18:12:00Z",
      "team": {
        "id": 1,
        "name": "Arsenal"
      }
    },
    {
      "id": 556,
      "title": "Желтая карточка",
      "value": "Enzo Fernandez",
      "matchMinute": 31,
      "sortOrder": 2,
      "occurredAt": "2026-05-18T18:31:00Z",
      "team": {
        "id": 2,
        "name": "Chelsea"
      }
    }
  ]
}
```

#### Сортировка событий

События должны возвращаться уже отсортированными сервером:

1. по `matchMinute`, если известна минута матча;
2. затем по `occurredAt`, если известно точное время;
3. затем по `sortOrder`;
4. затем по `id` как стабильный технический порядок.

Если в текущей БД нет этих полей, это та самая проблемка из задания 1: порядок
событий нужно добавить в модель или получать из источника данных при импорте.

### 4. Ошибки и пустые состояния

| Сценарий | HTTP status | Что возвращаем / показываем |
| --- | --- | --- |
| Некорректная дата | `400` | Ошибка валидации параметра `date`. |
| Некорректная timezone | `400` | Ошибка валидации параметра `timezone`. |
| Матч не найден | `404` | Матч отсутствует или недоступен пользователю. |
| Нет матчей за дату | `200` | `items: []`; клиент показывает пустой список матчей. |
| Нет событий в матче | `200` | `items: []`; клиент показывает "События отсутствуют". |
| Внутренняя ошибка | `500` | Стандартный формат ошибки API. |

### Что специально не делаем в API на этом этапе

- не добавляем фильтр событий по группам;
- не добавляем отдельный фильтр по статусу матча, потому что сейчас нужны только
  завершенные;
- не заставляем мобильное приложение собирать строку матча из нескольких запросов;
- не полагаемся на `Event.Id` как на бизнес-порядок событий.

## Задание 3. Проблемы модели данных и предложения по рефакторингу

### 1. У события нет времени или порядка внутри матча

**Проблема:** заказчик требует выводить события "в том порядке, как они произошли",
но в `Event` есть только `Id`, `Name`, `Category`, `Value`, `MatchId`. Эти поля не
гарантируют хронологический порядок.

**Предложение:**

- добавить `OccurredAt datetime null`;
- добавить `MatchMinute int null`, если спорт измеряется минутами матча;
- добавить `SortOrder int not null`, если источник данных отдает порядок событий;
- использовать `Id` только как последний tie-breaker, а не как бизнес-порядок.

### 2. `Event.Category` является числом без справочника

**Проблема:** числовая категория не самодокументирована. Непонятно, какие значения
допустимы и как их отображать.

**Предложение:**

- вынести тип события в справочник `EventType`;
- хранить `Event.EventTypeId` вместо сырого `Category` или рядом с ним на период
  миграции;
- в `EventType` хранить `Code`, `Name`, `EventGroupId`, `IconKey`, `SortOrder`.

Пример:

```text
EventType
- Id long
- Code string
- Name string
- EventGroupId long
- IconKey string
- SortOrder int
```

### 3. Связь `EventGroup` на схеме выглядит неоднозначно

**Проблема:** на схеме связь между `Event` и `EventGroup` подписана как `Has`, но
в таблице `Event` нет явного `EventGroupId`. При этом связь по кратности выглядит
как "у события есть группа".

**Предложение:**

- если группа относится к типу события, связать `EventType.EventGroupId`;
- если группа относится к конкретному событию, добавить `Event.EventGroupId`;
- предпочтительный вариант - группа через `EventType`, чтобы не дублировать данные
  у каждого события.

### 4. Команды в матче представлены полями `Opp1` и `Opp2`

**Проблема:** названия `Opp1` и `Opp2` не объясняют роли команд и не задают
ограничения ссылочной целостности. Связь `Team` - `Match` на схеме также выглядит
неоднозначно.

**Предложение:**

- заменить `Opp1` и `Opp2` на `HomeTeamId` и `AwayTeamId`, если спорт использует
  домашнюю/гостевую команду;
- либо создать таблицу `MatchParticipant`, если участников может быть больше двух
  или роли отличаются.

Вариант для двух команд:

```text
Match
- HomeTeamId long
- AwayTeamId long
```

Вариант для расширяемой модели:

```text
MatchParticipant
- Id long
- MatchId long
- TeamId long
- Role string
- Position int
```

### 5. Счет хранится строкой

**Проблема:** `FinalScore string` удобно отображать, но неудобно фильтровать,
валидировать и использовать в аналитике.

**Предложение:**

- добавить структурированные поля `HomeScore int`, `AwayScore int`;
- оставить `FinalScoreDisplay string` для отображения, если формат может быть
  сложным;
- для спортивных дисциплин с партиями/сетами рассмотреть отдельную таблицу
  `MatchScorePeriod`.

### 6. Статус матча выражен только булевыми флагами

**Проблема:** `Start bool` и `IsFinished bool` не покрывают реальные статусы:
запланирован, идет, завершен, отменен, перенесен, приостановлен.

**Предложение:**

- заменить или дополнить флаги полем `Status`;
- допустимые значения оформить enum/справочником:
  `scheduled`, `live`, `finished`, `cancelled`, `postponed`, `suspended`.

### 7. У `Team` есть `ChampId`

**Проблема:** команда может участвовать в разных чемпионатах или сезонах.
Прямая связь `Team.ChampId` ограничивает модель и может привести к дублированию
одной команды для разных чемпионатов.

**Предложение:**

- убрать жесткую принадлежность команды к одному чемпионату;
- добавить связующую таблицу `ChampTeam` или `SeasonTeam`.

Пример:

```text
ChampTeam
- Id long
- ChampId long
- TeamId long
- Season string
```

### 8. У `Champ` есть `DateStart` и `DateEnd`, но нет сезона

**Проблема:** чемпионаты часто повторяются по сезонам. Без отдельной сущности
сезона сложно отличить "Premier League 2025/2026" от "Premier League 2026/2027".

**Предложение:**

- выделить сущность `Season` или `ChampSeason`;
- матчи привязывать к сезону, а не только к чемпионату.

### 9. Нет явных индексов для целевого сценария

**Проблема:** экран будет часто запрашивать матчи по дате и чемпионату, а события
по матчу и порядку.

**Предложение:**

- индекс на `Match(DateStart, ChampId)`;
- индекс на `Match(ChampId, DateStart)`, если фильтрация по чемпионату основная;
- индекс на `Event(MatchId, SortOrder)`;
- индекс на `Event(MatchId, MatchMinute, OccurredAt)`, если используются эти поля.

### 10. Нейминг и типы требуют унификации

**Проблема:** в модели смешаны `Id long`, `ChampId long`, `Country int`, `Category int`,
`Start bool`. Часть полей названа как сущность, а не как внешний ключ.

**Предложение:**

- использовать единый стиль внешних ключей: `CountryId`, `ChampId`, `MatchId`;
- для дат использовать `datetime`/`timestamp with timezone` в БД и ISO 8601 в API;
- для технических идентификаторов использовать один тип во всех таблицах.

## Рекомендуемая минимальная доработка модели для MVP

5. Добавить индексы:
   - `Match(DateStart, ChampId)`;
   - `Event(MatchId, SortOrder)`.
