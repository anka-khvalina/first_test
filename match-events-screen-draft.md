# Черновик документации: экран событий матча за вчерашний день

## Контекст задачи

Нужно подготовить мобильный экран, на котором пользователь видит события,
произошедшие в матчах чемпионата за вчерашний день.

Пользовательский сценарий:

1. Пользователь открывает экран событий.
2. Приложение показывает список матчей за вчерашний день.
3. Пользователь может отфильтровать список матчей по чемпионату.
4. Пользователь выбирает матч.
5. Приложение показывает события выбранного матча в порядке их появления по ходу матча.

Исходная модель данных на схеме содержит сущности:

- `Country`
- `Champ`
- `Match`
- `Team`
- `Event`
- `EventGroup`

## Задание 1. Вопросы заказчику и потенциальные ответы

| # | Вопрос заказчику | Зачем спрашиваем | Потенциальный ответ / предложение |

Отмененные/перенесенные матчи обсудить отдельно после появления статуса матча. |

Остальные фильтры добавить только после подтверждения необходимости. |

| 9 | Как сортировать список матчей? | Сортировка влияет на удобство выбора матча. | Сортировать по времени начала матча: от раннего к позднему. При равном времени - по названию чемпионата и командам. |

| 12 | Что означает `Event.Category` и где хранится справочник категорий? | Категория сейчас числовая, клиент не знает, как ее подписывать и какую иконку показывать. | Завести справочник типов событий или API-контракт с `type`, `title`, `iconKey`, `group`. |
| 13 | Как использовать `EventGroup`: для UI-секций, фильтров или только внутренней классификации? | Нужно понять, будет ли группа отображаться пользователю. | Использовать группу для секций/иконок только если это нужно в интерфейсе; предпочтительно связывать группу через тип события. |
| 14 | Нужна ли пагинация списка матчей? | За день может быть много матчей, особенно без фильтра по чемпионату. | Для списка матчей добавить пагинацию. События одного матча возвращать одним списком. |
| 15 | Нужна ли локализация названий чемпионатов, команд и событий? | Мобильный экран может использовать язык пользователя. | Передавать `locale`; сервер возвращает локализованные названия при наличии переводов. |
| 16 | Как часто экран должен обновляться? | Нужно понять, требуется realtime или достаточно ручного обновления. | Для вчерашнего дня достаточно загрузки при открытии и pull-to-refresh. Realtime не нужен. |

## Схематичный экран

Вариант ниже показывает один экран со списком матчей и раскрытой областью событий
для выбранного матча. В реальном мобильном UI события можно показывать либо под
выбранным матчем, либо на отдельном экране деталей матча.

```text
+------------------------------------------------+
| События матчей                                 |
| Вчера, 18 мая 2026                         [v] |
+------------------------------------------------+
| Фильтры                                        |
| [Все чемпионаты v]                             |
+------------------------------------------------+
| Матчи                                         |
|                                                |
| Premier League                                |
| Team A                         2 : 1   Team B |
| 18:30 CET                         Завершен    |
| [Смотреть события]                             |
|                                                |
| La Liga                                       |
| Team C                         0 : 0   Team D |
| 20:00 CET                         Завершен    |
| [Смотреть события]                             |
+------------------------------------------------+
| События выбранного матча                       |
| Team A 2 : 1 Team B                            |
|                                                |
| 12'  Желтая карточка    Team B / Player 5      |
| 34'  Гол                Team A / Player 10     |
| 57'  Замена             Team B                 |
| 78'  Гол                Team B / Player 9      |
| 86'  Гол                Team A / Player 11     |
+------------------------------------------------+
```

### Состояния экрана

| Состояние | Что показываем |
| --- | --- |
| Нет матчей за дату | Empty state: "Матчи за выбранную дату не найдены". |
| Фильтр по чемпионату не дал результатов | Empty state и возможность сбросить фильтр. |
| У выбранного матча нет событий | Текст "События отсутствуют" в блоке событий. |
| Данные загружаются | Skeleton/loader для фильтров и списка матчей. |
| Ошибка загрузки | Сообщение об ошибке и кнопка "Повторить". |

## Задание 2. Методы API для поддержки функциональности

Ниже описан вариант REST API. Если в проекте используется GraphQL или другой стиль,
контракты можно перенести без изменения бизнес-логики.

### 1. Получить список чемпионатов для фильтра

```http
GET /api/v1/championships
```

#### Query-параметры

| Параметр | Тип | Обязательный | Описание |
| --- | --- | --- | --- |
| `date` | `string` в формате `YYYY-MM-DD` | да | Дата, за которую строится экран. Для задачи передается вчерашняя дата. |
| `timezone` | `string` | да | IANA timezone пользователя, например `Europe/Moscow`. |
| `hasMatches` | `boolean` | нет | Если `true`, вернуть только чемпионаты с матчами за дату. |
| `countryId` | `number` | нет | Дополнительный фильтр по стране, если понадобится. |
| `locale` | `string` | нет | Локаль отображения, например `ru-RU`. |

#### Ответ

```json
{
  "items": [
    {
      "id": 123,
      "name": "Premier League",
      "country": {
        "id": 10,
        "name": "England",
        "code": "GB"
      },
      "matchesCount": 6
    }
  ]
}
```

#### Комментарии

- Метод нужен для построения фильтра по чемпионату.
- Если фильтр должен показывать только релевантные значения, сервер применяет
  `date` и `hasMatches=true`.

### 2. Получить список матчей за дату

```http
GET /api/v1/matches
```

#### Query-параметры

| Параметр | Тип | Обязательный | Описание |
| --- | --- | --- | --- |
| `date` | `string` в формате `YYYY-MM-DD` | да | Дата начала матча в выбранной таймзоне. |
| `timezone` | `string` | да | IANA timezone пользователя. |
| `championshipId` | `number` | нет | Фильтр по чемпионату. |
| `status` | `string` | нет | Например `finished`, если нужны только завершенные матчи. |
| `page` | `number` | нет | Номер страницы. |
| `pageSize` | `number` | нет | Размер страницы. |
| `locale` | `string` | нет | Локаль отображения. |

#### Ответ

```json
{
  "items": [
    {
      "id": 987,
      "championship": {
        "id": 123,
        "name": "Premier League"
      },
      "startAt": "2026-05-18T18:30:00Z",
      "endAt": "2026-05-18T20:20:00Z",
      "status": "finished",
      "isFinished": true,
      "score": {
        "home": 2,
        "away": 1,
        "display": "2:1"
      },
      "teams": {
        "home": {
          "id": 1,
          "name": "Team A"
        },
        "away": {
          "id": 2,
          "name": "Team B"
        }
      },
      "eventsCount": 12
    }
  ],
  "pagination": {
    "page": 1,
    "pageSize": 20,
    "total": 48
  }
}
```

#### Комментарии

- Метод является основным источником данных для списка матчей.
- Мобильному приложению не нужно отдельно запрашивать команды и чемпионаты для
  каждой строки списка.
- При выборе чемпионата клиент повторяет запрос с `championshipId`.

### 3. Получить события выбранного матча

```http
GET /api/v1/matches/{matchId}/events
```

#### Path-параметры

| Параметр | Тип | Описание |
| --- | --- | --- |
| `matchId` | `number` | Идентификатор матча. |

#### Query-параметры

| Параметр | Тип | Обязательный | Описание |
| --- | --- | --- | --- |
| `locale` | `string` | нет | Локаль отображения. |

#### Ответ

```json
{
  "match": {
    "id": 987,
    "championship": {
      "id": 123,
      "name": "Premier League"
    },
    "startAt": "2026-05-18T18:30:00Z",
    "status": "finished",
    "score": {
      "home": 2,
      "away": 1,
      "display": "2:1"
    },
    "teams": {
      "home": {
        "id": 1,
        "name": "Team A"
      },
      "away": {
        "id": 2,
        "name": "Team B"
      }
    }
  },
  "items": [
    {
      "id": 555,
      "type": "goal",
      "category": 1,
      "title": "Гол",
      "value": "Team A, Player 10",
      "matchMinute": 34,
      "sortOrder": 1,
      "occurredAt": "2026-05-18T19:04:00Z",
      "group": {
        "id": 1,
        "name": "Голы"
      },
      "team": {
        "id": 1,
        "name": "Team A"
      }
    }
  ]
}
```

#### Сортировка

События должны возвращаться уже отсортированными сервером:

1. по `matchMinute`, если известна минута матча;
2. затем по `occurredAt`, если известно точное время;
3. затем по `sortOrder`;
4. затем по `id` как стабильный технический порядок.

Если в текущей БД нет этих полей, их нужно добавить или сформировать при импорте
данных из внешнего источника.


#### Query-параметры

| Параметр | Тип | Обязательный | Описание |
| --- | --- | --- | --- |
| `locale` | `string` | нет | Локаль отображения. |

#### Ответ

```json
{
  "items": [
    {
      "category": 1,
      "type": "goal",
      "name": "Гол",
      "group": {
        "id": 1,
        "name": "Голы"
```

### 5. Ошибки и пограничные состояния

Рекомендуемые статусы:

| Сценарий | HTTP status | Комментарий |
| --- | --- | --- |
| Некорректная дата или timezone | `400` | Клиент передал невалидные параметры. |
| Матч не найден | `404` | `matchId` отсутствует или недоступен пользователю. |
| Нет матчей за дату | `200` | Вернуть пустой `items`, это не ошибка. |
| Нет событий в матче | `200` | Вернуть пустой `items`, это не ошибка. |
| Внутренняя ошибка | `500` | Стандартный формат ошибки API. |

### 6. Возможный агрегированный метод

Если критична скорость первого открытия экрана, можно добавить агрегированный метод:

```http
GET /api/v1/match-events-screen
```

Он возвращает чемпионаты и первую страницу матчей одним ответом:

```json
{
  "filters": {
    "championships": []
  },
  "matches": {
    "items": [],
    "pagination": {
      "page": 1,
      "pageSize": 20,
      "total": 0
    }
  }

```

Этот метод удобен для мобильного UI, но базовые методы выше все равно стоит иметь
отдельно: они проще тестируются и переиспользуются.

## Задание 3. Проблемы модели данных и предложения по рефакторингу

### 1. У события нет времени или порядка внутри матча

**Проблема:** заказчик требует выводить события "в том порядке, как они произошли",
но в `Event` есть только `Id`, `Name`, `Category`, `Value`, `MatchId`. Эти поля не
гарантируют хронологический порядок.

**Предложение:**

- добавить `OccurredAt datetime null`;
- добавить `MatchMinute int null`, если спорт измеряется минутами матча;
- добавить `SortOrder int not null`, если источник данных отдает порядок событий;
- использовать `Id` только как последний tie-breaker, а не как бизнес-порядок.

### 2. `Event.Category` является числом без справочника

**Проблема:** числовая категория не самодокументирована. Непонятно, какие значения
допустимы и как их отображать.

**Предложение:**

- вынести тип события в справочник `EventType`;
- хранить `Event.EventTypeId` вместо сырого `Category` или рядом с ним на период
  миграции;
- в `EventType` хранить `Code`, `Name`, `EventGroupId`, `IconKey`, `SortOrder`.

Пример:

```text
EventType
- Id long
- Code string
- Name string
- EventGroupId long
- IconKey string
- SortOrder int
```

### 3. Связь `EventGroup` на схеме выглядит неоднозначно

**Проблема:** на схеме связь между `Event` и `EventGroup` подписана как `Has`, но
в таблице `Event` нет явного `EventGroupId`. При этом связь по кратности выглядит
как "у события есть группа".

**Предложение:**

- если группа относится к типу события, связать `EventType.EventGroupId`;
- если группа относится к конкретному событию, добавить `Event.EventGroupId`;
- предпочтительный вариант - группа через `EventType`, чтобы не дублировать данные
  у каждого события.

### 4. Команды в матче представлены полями `Opp1` и `Opp2`

**Проблема:** названия `Opp1` и `Opp2` не объясняют роли команд и не задают
ограничения ссылочной целостности. Связь `Team` - `Match` на схеме также выглядит
неоднозначно.

**Предложение:**

- заменить `Opp1` и `Opp2` на `HomeTeamId` и `AwayTeamId`, если спорт использует
  домашнюю/гостевую команду;
- либо создать таблицу `MatchParticipant`, если участников может быть больше двух
  или роли отличаются.

Вариант для двух команд:

```text
Match
- HomeTeamId long
- AwayTeamId long
```

Вариант для расширяемой модели:

```text
MatchParticipant
- Id long
- MatchId long
- TeamId long
- Role string
- Position int
```

### 5. Счет хранится строкой

**Проблема:** `FinalScore string` удобно отображать, но неудобно фильтровать,
валидировать и использовать в аналитике.

**Предложение:**

- добавить структурированные поля `HomeScore int`, `AwayScore int`;
- оставить `FinalScoreDisplay string` для отображения, если формат может быть
  сложным;
- для спортивных дисциплин с партиями/сетами рассмотреть отдельную таблицу
  `MatchScorePeriod`.

### 6. Статус матча выражен только булевыми флагами

**Проблема:** `Start bool` и `IsFinished bool` не покрывают реальные статусы:
запланирован, идет, завершен, отменен, перенесен, приостановлен.

**Предложение:**

- заменить или дополнить флаги полем `Status`;
- допустимые значения оформить enum/справочником:
  `scheduled`, `live`, `finished`, `cancelled`, `postponed`, `suspended`.

### 7. У `Team` есть `ChampId`

**Проблема:** команда может участвовать в разных чемпионатах или сезонах.
Прямая связь `Team.ChampId` ограничивает модель и может привести к дублированию
одной команды для разных чемпионатов.

**Предложение:**

- убрать жесткую принадлежность команды к одному чемпионату;
- добавить связующую таблицу `ChampTeam` или `SeasonTeam`.

Пример:

```text
ChampTeam
- Id long
- ChampId long
- TeamId long
- Season string
```

### 8. У `Champ` есть `DateStart` и `DateEnd`, но нет сезона

**Проблема:** чемпионаты часто повторяются по сезонам. Без отдельной сущности
сезона сложно отличить "Premier League 2025/2026" от "Premier League 2026/2027".

**Предложение:**

- выделить сущность `Season` или `ChampSeason`;
- матчи привязывать к сезону, а не только к чемпионату.

### 9. Нет явных индексов для целевого сценария

**Проблема:** экран будет часто запрашивать матчи по дате и чемпионату, а события
по матчу и порядку.

**Предложение:**

- индекс на `Match(DateStart, ChampId)`;
- индекс на `Match(ChampId, DateStart)`, если фильтрация по чемпионату основная;
- индекс на `Event(MatchId, SortOrder)`;
- индекс на `Event(MatchId, MatchMinute, OccurredAt)`, если используются эти поля.

### 10. Нейминг и типы требуют унификации

**Проблема:** в модели смешаны `Id long`, `ChampId long`, `Country int`, `Category int`,
`Start bool`. Часть полей названа как сущность, а не как внешний ключ.

**Предложение:**

- использовать единый стиль внешних ключей: `CountryId`, `ChampId`, `MatchId`;
- для дат использовать `datetime`/`timestamp with timezone` в БД и ISO 8601 в API;
- для технических идентификаторов использовать один тип во всех таблицах.

## Рекомендуемая минимальная доработка модели для MVP

Для реализации описанного экрана без большого рефакторинга достаточно:

1. Подтвердить, что `Match.Opp1` и `Match.Opp2` - это ссылки на `Team.Id`.
2. Добавить событиям поле порядка: `SortOrder` или `OccurredAt`.
3. Добавить или зафиксировать справочник категорий событий.
4. Возвращать из API агрегированные DTO, где уже есть названия чемпионата, команд,
   счет, статус и отсортированные события.
5. Добавить индексы:
   - `Match(DateStart, ChampId)`;
   - `Event(MatchId, SortOrder)`.
