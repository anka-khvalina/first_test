# Черновик документации: экран событий матча за вчерашний день

## Контекст задачи

Нужно подготовить мобильный экран, на котором пользователь видит события,
произошедшие в матчах чемпионата за вчерашний день.

Исходная модель данных на схеме содержит сущности:

- `Country`
- `Champ`
- `Match`
- `Team`
- `Event`
- `EventGroup`

### Итог задания 1. Пользовательский сценарий

1. Пользователь открывает экран просмотра событий.
2. Приложение отображает список матчей, сгруппированный или отфильтрованный по
   выбранной дате.
3. По умолчанию приложение показывает матчи за вчерашний день.
4. Пользователь может изменить дату отбора матчей через фильтр даты.
5. Пользователь может дополнительно отфильтровать список матчей по чемпионату.
6. В списке матчей приложение отображает основные данные по каждому матчу:
   - название чемпионата;
   - команды-участники;
   - время начала матча;
   - финальный счет, если матч завершен;
   - статус матча.
7. Список матчей сортируется по времени начала матча от более раннего к более
   позднему.
8. Пользователь выбирает матч из списка.
9. Приложение открывает экран или блок событий выбранного матча.
10. Приложение отображает список событий матча в порядке их появления по ходу
    матча.
11. Если у выбранного матча нет событий, приложение отображает пустой список с
    текстом: "События отсутствуют".

## Задание 2. Методы API для поддержки функциональности

Ниже вариант REST API, переписанный уже по ответам из задания 1. Экрану нужны
дата, чемпионат, список завершенных матчей и события выбранного матча.

### 1. Получить список матчей при открытии экрана и изменении фильтров

```http
GET /api/v1/matches
```

Метод вызывается:

1. при открытии экрана с предвыбранными параметрами;
2. повторно, когда пользователь изменил дату;
3. повторно, когда пользователь изменил чемпионат.

На открытии экрана клиент вызывает:

```http
GET /api/v1/matches?date=2026-05-18
```

Если пользователь выбрал чемпионат:

```http
GET /api/v1/matches?date=2026-05-18&championshipId=123
```

#### Query-параметры

| Параметр | Тип | Обязательный | Описание |
| --- | --- | --- | --- |
| `date` | `string` в формате `YYYY-MM-DD` | да | Дата отбора матчей. На первом открытии клиент передает вчерашнюю дату. |
| `timezone` | `string` | нет | Таймзона для границ даты. Если договорились жить по серверному времени, параметр можно не передавать. |
| `championshipId` | `number` | нет | Фильтр по чемпионату. |

#### Правила выборки

- матчи выбираются по `Match.DateStart`;
- показываем только завершенные матчи: `IsFinished = true`;
- если матч начался вчера, а закончился сегодня, он все равно относится ко вчерашней
  дате;
- список матчей сортируется по времени начала от раннего к позднему;
- параметр `status` с клиента не нужен: по текущему решению всегда возвращаем
  завершенные матчи;
- фильтра по группам событий нет: клиент сказал, что он не нужен.

#### Ответ

```json
{
  "items": [
    {
      "id": 987,
      "championship": {
        "id": 123,
        "name": "English Premier League"
      },
      "startAt": "2026-05-18T18:00:00Z",
      "status": "finished",
      "score": {
        "home": 2,
        "away": 1,
        "display": "2:1"
      },
      "teams": {
        "home": {
          "id": 1,
          "name": "Arsenal"
        },
        "away": {
          "id": 2,
          "name": "Chelsea"
        }
      },
      "eventsCount": 6
    }
  ]
}
```

#### Комментарии

- это основной метод для открытия экрана и последующего изменения фильтров;
- сортировка серверная: `DateStart ASC`;
- если матчей нет, возвращаем `items: []`, а клиент показывает пустое состояние.

### 2. Получить список чемпионатов для фильтра

```http
GET /api/v1/championships
```

Метод нужен, если фильтр чемпионата перезагружается отдельно от списка матчей.

#### Query-параметры

| Параметр | Тип | Обязательный | Описание |
| --- | --- | --- | --- |
| `date` | `string` в формате `YYYY-MM-DD` | да | Дата, для которой строим фильтр. |
| `timezone` | `string` | нет | Таймзона для границ даты. |

#### Ответ

```json
{
  "items": [
    {
      "id": 123,
      "name": "English Premier League",
      "matchesCount": 2
    }
  ]
}
```

#### Комментарии

- возвращаем только чемпионаты, где есть завершенные матчи за выбранную дату;
- на клиенте дополнительно добавляем вариант "Все чемпионаты".

### 3. Получить события выбранного матча

```http
GET /api/v1/matches/{matchId}/events
```

#### Path-параметры

| Параметр | Тип | Описание |
| --- | --- | --- |
| `matchId` | `number` | Идентификатор выбранного матча. |

#### Query-параметры

Не нужны. Особенно не нужен фильтр по группам событий: клиент ответил отрицательно,
так что не плодим лишнюю ручку/параметр без пользы.

#### Ответ

```json
{
  "match": {
    "id": 987,
    "championship": {
      "id": 123,
      "name": "English Premier League"
    },
    "startAt": "2026-05-18T18:00:00Z",
    "status": "finished",
    "score": {
      "home": 2,
      "away": 1,
      "display": "2:1"
    },
    "teams": {
      "home": {
        "id": 1,
        "name": "Arsenal"
      },
      "away": {
        "id": 2,
        "name": "Chelsea"
      }
    }
  },
  "items": [
    {
      "id": 555,
      "title": "Гол",
      "value": "Bukayo Saka",
      "matchMinute": 12,
      "sortOrder": 1,
      "occurredAt": "2026-05-18T18:12:00Z",
      "team": {
        "id": 1,
        "name": "Arsenal"
      }
    },
    {
      "id": 556,
      "title": "Желтая карточка",
      "value": "Enzo Fernandez",
      "matchMinute": 31,
      "sortOrder": 2,
      "occurredAt": "2026-05-18T18:31:00Z",
      "team": {
        "id": 2,
        "name": "Chelsea"
      }
    }
  ]
}
```

#### Сортировка событий

События должны возвращаться уже отсортированными сервером:

1. по `matchMinute`, если известна минута матча;
2. затем по `occurredAt`, если известно точное время;
3. затем по `sortOrder`;
4. затем по `id` как стабильный технический порядок.

Если в текущей БД нет этих полей, это та самая проблемка из задания 1: порядок
событий нужно добавить в модель или получать из источника данных при импорте.

### 4. Ошибки и пустые состояния

| Сценарий | HTTP status | Что возвращаем / показываем |
| --- | --- | --- |
| Некорректная дата | `400` | Ошибка валидации параметра `date`. |
| Некорректная timezone | `400` | Ошибка валидации параметра `timezone`. |
| Матч не найден | `404` | Матч отсутствует или недоступен пользователю. |
| Нет матчей за дату | `200` | `items: []`; клиент показывает пустой список матчей. |
| Нет событий в матче | `200` | `items: []`; клиент показывает "События отсутствуют". |
| Внутренняя ошибка | `500` | Стандартный формат ошибки API. |

### Что специально не делаем в API на этом этапе

- не добавляем фильтр событий по группам;
- не добавляем отдельный фильтр по статусу матча, потому что сейчас нужны только
  завершенные;
- не заставляем мобильное приложение собирать строку матча из нескольких запросов;
- не полагаемся на `Event.Id` как на бизнес-порядок событий.

## Задание 3. Проблемы модели данных и предложения по рефакторингу

| # | Объект / связь | Проблема | Почему это проблема | Что предложить |
| -: | --- | --- | --- | --- |
| 1 | `Event` | Нет поля времени события | По требованию события нужно показывать "в порядке как они произошли", но в таблице нет минуты / секунды / timestamp события | Добавить `EventMinute`, `EventSecond`, `EventOrder` или `EventTime` |
| 2 | `Event.Value string` | Поле слишком абстрактное | Непонятно, что хранится в `Value`: минута, счет, описание, тип события, игрок? Это усложняет API и сортировку | Разделить на понятные поля: `Minute`, `Description`, `ScoreAfterEvent`, `PayloadJson` |
| 3 | `Event.Category int` | Неясно, что такое `Category` | Есть отдельная таблица `EventGroup`, но в `Event` нет явного `EventGroupId`. Связь нарисована, но поле называется неочевидно | Переименовать `Category` в `EventGroupId` или добавить отдельную таблицу `EventType` |
| 4 | `Event` -> `EventGroup` | Неправильная детализация событий | `EventGroup` может быть "Card", а конкретный тип события - "Yellow Card" или "Red Card". Сейчас группа и тип смешиваются | Добавить `EventType`: `Goal`, `Yellow Card`, `Red Card`, `Substitution`, `Penalty` |
| 5 | `Event` | Нет ссылки на команду | Нельзя понять, к какой команде относится событие: гол Arsenal или Chelsea, карточка какой команды | Добавить `TeamId` в `Event` |
| 6 | `Event` | Нет ссылки на игрока | Для футбольных событий часто нужен игрок: кто забил, кто получил карточку, кого заменили | Для MVP можно оставить `PlayerName string`, лучше - добавить `Player` |
| 7 | `Match.Opp1`, `Match.Opp2` | Непонятные названия полей | `Opp1` и `Opp2` не говорят, кто домашняя команда, кто гостевая, а это важно для отображения | Переименовать в `HomeTeamId`, `AwayTeamId` или хотя бы `Team1Id`, `Team2Id` |
| 8 | `Match.FinalScore string` | Счет хранится строкой | Строка `2:1` удобна для показа, но неудобна для фильтрации, аналитики и валидации | Хранить `HomeScore int`, `AwayScore int`, а `FinalScore` формировать на чтении |
| 9 | `Match.Start bool` | Поле непонятное | Есть `DateStart`, но еще есть `Start bool`. Неясно, это "матч начался" или "стартовый матч" | Заменить на нормальный `MatchStatus`: `Scheduled`, `Live`, `Finished`, `Cancelled`, `Postponed` |
| 10 | `Match.IsFinished bool` | Слишком слабый статус | Булево поле не позволяет различать отмененный, перенесенный, live, прерванный матч | Использовать `Status`, а `IsFinished` при необходимости считать производным |
| 11 | `Match.DateStart`, `DateEnd` | Нет timezone | Требование "за вчерашний день" зависит от часового пояса: пользователя, сервера или чемпионата | Хранить `DateStartUtc`, `DateEndUtc` + timezone чемпионата / страны |
| 12 | `Team.ChampId` | Команда привязана к одному чемпионату | Команда может играть в разных турнирах: лига, кубок, международные турниры | Убрать `ChampId` из `Team`, добавить связующую таблицу `ChampTeam` |
| 13 | `Champ.Country int` | Название поля неявное | Непонятно, это код страны или внешний ключ на `Country.Id` | Переименовать в `CountryId` |
| 14 | `Country` -> `Champ` | Связь подписана `Goes In` странно и не по смыслу | Лучше явно: страна имеет чемпионаты / чемпионат проводится в стране | Назвать связь `Country has Championships` |
| 15 | `Champ` | `DateStart`, `DateEnd` как `date`, но нет сезона | Для чемпионатов чаще важен сезон: `2025/2026`, а не просто даты | Добавить `Season`, даты оставить как технический период |
| 16 | `Match` | Нет названия / описания матча | Для API придется каждый раз собирать `Arsenal vs Chelsea` через команды | Не обязательно хранить, но в API формировать `matchName` |
| 17 | `Match` | Нет индексов под основной сценарий | Экран будет часто искать матчи за дату и чемпионат | Индексы: `Match(DateStart, ChampId, IsFinished)`, `Event(MatchId, EventOrder)` |
| 18 | `Event` | Нет гарантии порядка событий | Даже если добавить минуту, два события могут быть на одной минуте | Добавить `EventOrder` или `CreatedAt` |
| 19 | `Event` | Нет технического времени создания / обновления | Сложнее отлаживать, синхронизировать и обновлять события | Добавить `CreatedAt`, `UpdatedAt`, возможно `SourceSystem` |
| 20 | `Event` | Нет внешнего идентификатора события | Если события приходят из внешнего провайдера, нужен id провайдера для дедупликации | Добавить `ExternalEventId`, `Provider` |
| 21 | `Event` | Нет признака удаления / отмены события | В спорте события могут корректироваться: отмененный гол, VAR, изменение карточки | Добавить `IsCancelled` / `Status` |
| 22 | `EventGroup` | Только `Name`, нет кода | По имени неудобно интегрироваться и локализовать | Добавить `Code`, например `GOAL`, `CARD`, `SUBSTITUTION` |
| 23 | Все таблицы | Нет аудита | Нет `CreatedAt`, `UpdatedAt`, а для событий это важно | Добавить audit fields |
| 24 | Все связи | Кардинальности выглядят спорно | Например связь Team-Match нарисована неочевидно: матч имеет две команды, но команда играет во многих матчах | Перерисовать связи через `HomeTeamId`, `AwayTeamId` |

### Что бы я предложила как минимальный рефакторинг

Чтобы не перестраивать всю модель с нуля, можно сделать минимально достаточную доработку:

#### Event

```text
Event
- Id long
- MatchId long
- EventGroupId int
- EventTypeId int
- TeamId long nullable
- Name string
- Description string
- EventMinute int
- EventSecond int nullable
- EventOrder int
- Value string nullable
```

#### EventType

```text
EventType
- Id int
- EventGroupId int
- Name string
- Code string
```

Пример:

| EventGroup | EventType |
| --- | --- |
| Goal | Goal |
| Card | Yellow Card |
| Card | Red Card |
| Substitution | Substitution |
| Match State | Kick Off |
| Match State | Half Time |
| Match State | Full Time |

#### Match

```text
Match
- Id long
- ChampId long
- DateStartUtc datetime
- DateEndUtc datetime
- Status string
- HomeTeamId long
- AwayTeamId long
- HomeScore int
- AwayScore int
```

### Что можно оставить как есть для MVP

| Можно оставить | Почему |
| --- | --- |
| Country | Достаточно простая таблица |
| Champ | В целом ок, если переименовать Country в CountryId |
| EventGroup | Можно оставить как справочник групп |
| FinalScore string | Можно временно оставить для отображения, но лучше потом заменить структурным счетом |
| Team.ChampId | Можно временно оставить, если точно команда играет только в одном чемпионате в рамках MVP |

### Что обязательно поправить перед реализацией экрана

| Приоритет | Что поправить | Почему |
| --- | --- | --- |
| Must have | Добавить время / порядок события в Event | Без этого нельзя выполнить основное требование |
| Must have | Добавить связь события с типом события | Чтобы понимать, что именно произошло |
| Must have | Добавить корректную связь события с группой события | Сейчас Category int неочевиден |
| Should have | Добавить TeamId в Event | Чтобы показывать команду события |
| Should have | Переименовать Opp1/Opp2 | Чтобы не путаться в командах |
| Should have | Добавить MatchStatus | Чтобы корректно фильтровать завершенные матчи |
| Could have | Добавить Player | Полезно для красивого отображения, но можно заменить PlayerName string |

### Короткий вывод

Текущая модель подходит только для очень грубого хранения: “есть матч, у него есть какие-то события”.

Но для мобильного экрана, где нужно показывать события понятно, красиво и в хронологическом порядке, модели не хватает:

- времени события;
- типа события;
- команды события;
- нормального статуса матча;
- структурного счета;
- понятных связей между командами, матчами и чемпионатами.

То есть модель не катастрофа, но ей срочно нужен ремень безопасности перед выездом на прод.
